# 设计说明

这份文档记录几个决定是怎么做出来的，以及哪些地方还没做好。功能清单和运行方式在 [README](../README.md)。

## 一、要解决的问题

安化黑茶的门槛不在喝，在认。

**品类记不住。** 「三尖、三砖、一卷」是行话，官茶沿革、万里茶道路线、非遗工序又散在县志、茶厂史料和口述里。普通人很难在半小时内搭起框架，网上现成的内容多是软文，没法检索。

**真假分不清。** 茯砖里的「金花」是冠突散囊菌，受潮长的霉是杂菌，两者在外观上有相似之处。没有对照工具，两种错误都会发生：把霉茶当金花喝，把好砖当发霉扔掉。

**接不上。** 黑茶的传播形象偏「老」，冲泡被当成有门槛的事。新茶友缺选购、冲泡、存放的入门参数，也缺一个能提问的地方。

三件事对应三类功能：结构化档案、对照式判别、低门槛问答与个人记录。

## 二、功能与信息架构

七个页面，哈希路由，每个视图是一个模块，负责渲染和清理自己的状态。

| 页面 | 内容 |
| --- | --- |
| 首页 | 茶山主视觉、四条浏览线索、三个入口、万里茶道横幅 |
| 茶品档案 | 12 条记录，按品类筛选、文字搜索、2–3 款并排对比、详情面板 |
| 万里茶道 | 11 个节点顺序导览，配 10 个历史节点的时间轴 |
| 千两茶技艺 | 10 道工序，前后切换，会话内记住进度 |
| 金花鉴别 | 金花与霉变六维对照、菌相示意 SVG、五道自测 |
| AI 茶博士 | 流式问答，模型选择，可中止、可重开 |
| 我的茶仓 | 未登录用本机存储；登录后写云端，公开笔记进茶友圈 |

本机茶仓不需要账号，数据存在 `localStorage`，支持 JSON 导出、合并导入、重复跳过和坏文件保护。云端茶仓的三张表都有行级安全策略，公开笔记只读，私人存茶只有本人可见。

## 三、技术选择

**原生 HTML/CSS/JS，没有构建步骤。** 页面数量可控，引框架只会增加阅读和部署成本。代价是路由、弹窗、焦点管理这些要自己写。

**哈希路由 + 视图注册表。** 静态托管不需要服务端重写规则；每个视图返回一个清理函数，切页时取消未完成的请求、解绑监听。

**云端是可选能力。** `js/config.js` 里三档：`auto` 只在配置域名下初始化，`enabled` 供授权域名显式开启，`disabled` 关闭。SDK 从 CDN 改为随包固定版本并异步加载，8 秒上限；加载失败不影响文化内容。

**单文件构建。** `scripts/build-standalone.py` 把 index.html 引用的 css/js/图片/favicon 全部内联成 `离线体验.html`，用来发给没有开发环境的人。

**缓存用内容哈希。** 托管环境不下发 `Cache-Control`，浏览器按 `Last-Modified` 做启发式缓存，改完代码访客可能还看旧页面。`index.html` 里的引用都带文件 sha256 前 8 位，`scripts/stamp-assets.py` 重算；字体分片文件名唯一，不加版本号。

## 四、数据与权限

三张表：`tea_archives`（公开读，仅管理端写）、`tea_notes`（公开读，本人写）、`tea_cellar`（本人读写）。

写策略只对 `authenticated` 角色生效：

```sql
CREATE POLICY tea_notes_write_own ON tea_notes FOR ALL TO authenticated
  USING (owner_id = auth.uid()) WITH CHECK (owner_id = auth.uid());
```

**为什么不是 `TO authenticated, anon`。** 平台给未登录请求返回的身份标识是字符串 `anon`，不是 `NULL`。如果把 `anon` 写进策略，条件会变成 `'anon' = 'anon'`，判定通过，匿名访客可以直接写库；而且所有匿名访客共享同一个标识，彼此的数据互相可见。

这不是推演出来的。上线后实测，未登录状态确实写进去了。收窄角色范围后复测：写入返回 `42501`，读私有表返回 0 行，公开读取不受影响，测试数据已清理。

**已知限制。** `tea_notes` 为了公开茶友圈，对访客开放整行读取，返回里包含作者的内部标识。这个标识不可逆、不含邮箱，但更干净的做法是用视图只暴露必要列，目前还没做。

## 五、AI 的边界

茶博士不是把通用模型套个聊天框。系统提示词里内置了一份按板块整理的安化黑茶知识库（品类、历史、产地、工艺、金花鉴别、冲泡、选购、存储、梅山文化、万里茶道），并定了六条规则：

1. 只依据知识库与公认茶学常识作答，不确定就说「这一点我无法确认」
2. 简体中文，面向普通消费者
3. 操作性问题给可执行的具体参数
4. 健康相关只做常识描述，不宣称疗效
5. 不推荐品牌、商家、价格
6. 回答控制在 400 字以内

输出一律用 `textContent` 渲染，不拼 HTML；对话不写库、不留存、不训练。界面上标了「仅供作品鉴与文化科普参考」。

这些约束不能保证回答正确。它的作用是让「不知道」这件事能被看见。

## 六、测试与验证

**本地回归（23 项）。** Playwright + 本地静态服务器，四种视口（1440 / 768 / 390 / 320），真实点击七个路由：筛选、搜索、对比、详情、弹窗焦点、键盘导航、茶道与工序进度、自测题、本机茶仓的增删改导出导入、坏数据保护、离线状态、无横向溢出。外部请求全部拦截。

**协议回归（12 项）。** 直接加载 `vendor/` 里未改动的 SDK，用本地 HTTP fixture 返回后端原始 JSON / SSE：密码登录与会话恢复、OTP 注册与重置、退出失败时本地会话清理、停用模型过滤、默认模型、完整 SSE、异常断流、HTTP 取消、无模型降级、数据库过滤与 Bearer 头。

**上线后实测。** 在正式域名下检查过：静态资源全部 200；云端读到 12 条档案；模型目录返回 31 个可用模型；流式调用能返回内容；错误账号登录返回凭据错误；未登录写入返回 42501；未登录读私有表返回 0 行。日志和结果在 `docs/verification/`。

**没覆盖的。** 真实邮箱投递、邮件模板、找回密码的完整链路；模型回答质量；跨账号并发；手机 Safari 和微信内置浏览器。本地测试用的是 SDK 替身和本地 fixture，能说明前端逻辑，不能替代真实环境验收。

## 七、已知限制与后续

- 茶品档案的年份、产地、工艺表述还没逐条做过文献审查，正式对外前需要人工核一遍
- 金花配图是 AI 生成的示意图，判定依据是六维文字对照，不是图
- 云端数据没有导出和账号注销，本机茶仓有导出
- 图像识别辅助判断金花，目前只是规划
- 手机端适配做了 390 / 320 两档，真机覆盖还不够
